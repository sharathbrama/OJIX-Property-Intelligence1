# OJIX MVP production audit

**Date:** 12 November 2026  
**Scope:** repository/configuration inspection and Phase 3 isolated MariaDB migration rehearsal. No production account, database, deployed service, customer data, or production secret was accessed. Historical SQL ran only against `ojix_migration_rehearsal` on the dedicated MariaDB 10.11.19 test container. No migration source was changed.

## Executive status

The repository contains a substantial multi-role property case management application, not a Firebase-only application. Its operational data plane is an Express API backed by MariaDB, private file storage, and a separate Python/Tesseract job worker. Firebase Hosting can serve the built React application, but the current Hosting configuration cannot serve or proxy those services. There is no zero-cost, Firebase Spark-only deployment that preserves the existing workflows and their security model.

**Release decision: blocked for real client data and for a complete Firebase Hosting deployment.** Suitable next step is a controlled internal MVP deployment on already available infrastructure that can run Node, Python and MariaDB, with private durable storage; if no such infrastructure exists, the no-cost Firebase-only option is a static UI demonstration with backend-dependent workflows unavailable. Do not represent it as a production application.

## Important findings and blockers

1. **Firebase API routing is broken for the configured Hosting target.** `apps/web/src/apiConfig.ts` sets `API_BASE_URL = ''`, so the browser calls `/api/...` on the Hosting origin. `firebase.json` rewrites all paths, including `/api/*`, to `/index.html`; this returns application HTML, not API JSON. No Cloud Functions/Run rewrite or separate API URL is configured. Firebase Hosting cannot execute the Express server.
2. **Spark does not host this backend stack.** Express, continuous Python OCR worker and MySQL/MariaDB need compute and database services. Firebase Spark does not provide these. Cloud Functions/Cloud Run deployment or Firebase-to-cloud integrations that require Blaze involve billing; do not create or enable paid resources without authorization.
3. **Data and document persistence are mandatory.** Hosting the UI alone leaves no secure API, relational data, private document service, or OCR queue. Never expose the API anonymously or route private document requests to the SPA fallback.
4. **Authentication wiring is mixed.** The UI is designed around API OTP sessions; Firebase is present as a dependency and optional API token verifier, but there is no evidence of complete Firebase web sign-in/token refresh configuration. Environment variables in `.env.example` describe server settings and optional Vite Firebase settings; no production values were read.
5. **Production source integrations are not configured by repository defaults.** RTC provider defaults disabled; source registry connectors cannot be treated as verified live government lookups. GIS imports require licence/provenance/quality checks.
6. **PDF is unavailable.** API responds 501 for PDF export; Word/JSON options exist for approved consultant reports. A prior architecture review warns against mock PDF bytes; current `server.ts` explicitly refuses PDF.
7. **Security controls are incomplete for confidential client records.** No production storage/IAM/network/backups, malware scan, file signature checks, retention execution, restore drill or independent security assessment was evidenced. Server guards are promising but need complete role and tenant test coverage.
8. **Schema/migration governance blocks production rollout.** The 31 files are contiguous 004–034, but there is no runner or version ledger. API startup explicitly avoids DDL; Docker initializes `database/mysql-schema.sql` then `infra/db/seed.sql`, while README documents selected manual migrations rather than a complete deployment sequence. All 31 migrations passed on the isolated MariaDB 10.11.19 test DB using the tracked older `database/mysql-schema.sql.bak` as a reconstructed candidate baseline. That backup has no version/checksum proving it matches a deployed schema. Catalog verification found all 44 tables and 515 columns matching the canonical schema, but migration 034 creates a viewer-assignment index missing from canonical DDL. Migration 026 also changes seeded `user-super-admin` to `owner`; 3 of 473 API tests failed on Super Admin/role assertions (470 passed). Migration 031 remains one-shot and was not rerun. Full detail is in `docs/DATABASE_MIGRATION_REHEARSAL.md`. Do not infer production migration history from filenames, backup name, or canonical schema.

### Phase 2 verification (11 November 2026)

- The duplicate was the fourth `CREATE TABLE` statement (the second declaration for `workspace_purge_requests`, lines 53–69 before repair). It was an exact duplicate, not a conflicting definition or ordering defect.
- The single remaining definition retains all 10 columns, primary key, tenant/status index, and both foreign keys. It matches the canonical schema definition in `database/mysql-schema.sql`; the other two tables in 031 also match their canonical schema definitions.
- Migration order is numeric: 031 follows 030 and precedes 032. Its prerequisites `organizations` and `documents` are established earlier. Migration 032 alters the OCR job table from migration 028. The repository lacks a migration runner/history record, so numeric filenames alone do not prove deployment history.
- A fresh MariaDB 10.11 disposable database with prerequisite tables and seeded organization/document rows was backed up before 031. The repaired migration created all three intended tables; both pre-existing rows remained; the purge table had two foreign keys and the expected tenant/status index. No existing application database was accessed.
- Reapplying 031 to a second backed-up disposable MariaDB 10.11 database failed as expected with error 1050 at the first existing table (`owner_configuration_versions`); all three created tables and both prerequisite fixture rows remained. This confirms 031 is one-shot, not idempotent.
- The full API suite passed 473/473 against a separately initialized and backed-up disposable MariaDB 10.11 database. API TypeScript build passed. Details are in `docs/PRODUCTION_TEST_REPORT.md`.

### Phase 3 migration rehearsal (12 November 2026)

- All 31 migration files, numbered 004–034, passed in numeric order on isolated MariaDB 10.11.19. The rehearsal database used a filtered copy of tracked `database/mysql-schema.sql.bak`; the current canonical schema is not a valid replay baseline because many migration changes are already present there.
- Static dependency review found expected prerequisites: 004 requires base `properties`; 007 requires `properties` and `organizations`; 013 establishes account/OTP tables before 017/019/026/027; 015/017/028/030 add to base properties/documents and later migrations consume the resulting tables/columns; 032 depends on migration 028's OCR job table; 031 depends on base `organizations` and `documents`; 034 depends on 030's `assigned_consultant_uid`.
- Schema verification found 44/44 canonical table names, 515/515 canonical column names, all 63 explicitly named canonical indexes, 72 foreign keys, and zero orphaned rows. Migration 034's `property_viewer_assignment_idx` exists in the upgraded schema but is missing from canonical fresh-install DDL.
- One seeded organization, 11 memberships, one seeded property, and one synthetic spatial layer were present. No `user_accounts` rows were expected from `infra/db/seed.sql`. Migration 026 changed `user-super-admin` from `super_admin` to `owner`; the API suite on the migrated database had 470 pass and 3 Super Admin/role failures.
- Migrations 007/008 received supplemental backfill/replay checks with a clearly synthetic legacy property. Migration 031 ran once. Detailed execution, errors during baseline preparation, object comparisons, and risks are in the migration rehearsal report.
- The tracked backup is only a candidate baseline; no ledger or version metadata proves it is the exact predecessor of a deployed schema. The rehearsal therefore establishes compatibility with that candidate, not a safe production target path.
9. **Configuration drift exists.** Root scripts/documentation mention different API ports, database targets and Firebase sign-in readiness. Firebase Hosting config currently says public `apps/web/dist`; build must be confirmed before deployment. `.firebaserc` selects project `ojix-property-intelligence`, but this does not prove access, billing state, auth setup or production readiness.

## Required next changes, in order

1. Choose and document an actual runtime for API, MariaDB-compatible database, OCR worker and private files. Under the stated restrictions, use existing approved/on-prem infrastructure if available; otherwise stop short of client data and use the Firebase-hosted static demo only.
2. Give the frontend an explicit production API base URL (or configure a supported proxy to the separately hosted API), exact CORS allowlist, TLS, health/readiness checks, and fail-fast startup. Ensure API paths can never fall through to `index.html`.
3. Reconcile canonical schema, seeds and migrations; review and approve a migration ledger/runner design before implementation; rehearse forward upgrade and restore on disposable database copies. Preserve and back up existing MySQL/MariaDB; no Firestore migration in this phase.
4. Complete production identity setup: verified OTP email/SMS provider or a fully implemented Firebase Authentication flow; enforce server-side account/workspace/RBAC checks, remove dev/demo paths in prod builds, test expiry/revocation/recovery and tenant boundaries.
5. Configure private durable document storage with least-privilege service credentials, signature/type validation, size limits, malware quarantine, retention/legal hold/deletion, audited downloads, encryption and restore procedures.
6. Deploy OCR worker with private queue/API access, bounded resource use, retries, monitoring and reviewer confirmation. Validate Kannada/English scanned-PDF quality with representative synthetic documents. Keep uncertain fields flagged; human review is required.
7. Implement and verify real PDF rendering or keep PDF unavailable in product. Validate escaped report content, approved snapshots, source provenance and export authorization.
8. Run the required frontend/backend TypeScript builds, unit, RBAC, auth, OCR, migration and API integration tests; add cross-tenant authorization tests and deployment smoke tests. Record exact commands and outputs in the test report.
9. Only after architecture/API reachability is proven, build and deploy the frontend to Hosting. No deploy, GitHub push, paid-resource creation, or production DB change was performed in this audit.

## Audit limitations

The full SQL sequence was tested only against the reconstructed `.bak` candidate, not an actual pre-release or production database copy. Backfill behavior was tested with synthetic data, not historical customer distributions; migrations 020 and 025 had no matching rows to delete. No production or pre-existing database was contacted. No Firebase console, secret manager, SMTP, storage account, API host, or production logs were accessed. No deployment, push, migration-ledger implementation, or source migration change occurred.
