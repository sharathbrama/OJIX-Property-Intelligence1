## 1. Executive summary

The release compiles, passes TypeScript validation, produces a successful production build, and passes the available frontend property-form unit tests. The source review and secret-pattern scan found no obvious committed private keys or access tokens.

The complete API test suite could not be certified in the current run because it requires MariaDB on `127.0.0.1:3306` and a running API on port `4000`. Those services were unavailable, so the affected tests failed with `ECONNREFUSED`. This is an environment/setup blocker, not evidence that the assertions themselves are defective; however, a release cannot receive a full QA pass until the suite runs successfully in the required environment.

This build may be used for internal demonstrations and controlled QA with synthetic data. It must not be represented as production-ready legal verification software or be used with real client documents until the critical release gates in Section 8 are closed.

## 6. Defects, risks and observations

### High priority

**QA-RISK-01 — Full regression result is unavailable**  
The main API suite depends on MariaDB and a running API. Until the required services are started and the entire suite passes, regressions in authorization, tenant isolation, document access, title events and spatial HTTP routes cannot be ruled out.

**QA-RISK-02 — Database migrations are not release-certified**  
Migrations `019–025` introduce authentication/account changes. They need forward-migration tests using a copy of the previous schema, clean-install tests, data-integrity checks and a documented recovery procedure.

**QA-RISK-03 — Production identity and OTP delivery are unverified**  
Real Firebase and SMTP configurations were not exercised. Production sign-in, OTP expiry, retry/rate limits, account recovery, delivery failures and audit events require verification.

**QA-RISK-04 — Real client-data controls are incomplete or unverified**  
Private durable storage, malware scanning/quarantine, retention/deletion, encryption/IAM, export auditing and restore testing are not certified. Real client documents must not be uploaded.

### Medium priority

**QA-RISK-05 — Frontend bundle is large**  
The main JavaScript output is approximately 1.68 MB before gzip (approximately 442 KB gzip). Route-based code splitting and manual chunking should be considered, followed by measured performance testing on representative devices and networks.

**QA-RISK-06 — OCR quality is not benchmarked**  
No approved representative corpus, field-level accuracy target, Kannada/English coverage threshold or human-review acceptance criteria were supplied.

**QA-RISK-07 — Browser E2E coverage is missing**  
Critical user journeys have not been proven through the rendered UI, including registration, OTP, property creation, upload, OCR review, title chain, spatial state, report export and administrative actions.

### Low priority

**QA-RISK-08 — Markdown trailing whitespace**  
Three lines in `docs/audit/P0-GAP-REGISTER.md` were reported by `git diff --check`. These appear to be Markdown hard line breaks and have no application runtime impact.

## 7. Required end-to-end acceptance scenarios

The following scenarios should be executed before release approval:

1. Register a new user, verify email and optional phone OTP, sign in, sign out and verify session invalidation.
2. Confirm invalid, expired, reused and rate-limited OTP behavior without exposing codes in logs or responses.
3. Create agricultural and non-agricultural property cases; verify validation, persistence and reload behavior.
4. Upload each supported file type; verify size/type rejection, checksum, tenant isolation, download authorization and audit logs.
5. Run OCR on representative Kannada and English documents; compare extracted fields against an approved answer key and complete human review.
6. Build and edit a title chain; confirm rationale requirements, immutable audit history and role restrictions.
7. Run spatial screening with verified, unverified and missing datasets; ensure the UI never implies official clearance when evidence is unavailable.
8. Generate and retrieve reports; verify escaping, evidence links, missing-data disclosures and access control.
9. Verify every role: Owner, Admin, Lawyer, Analyst, Operations, Consultant, Support, Data Steward and Viewer.
10. Attempt cross-tenant access for properties, documents, reports, memberships and audit records; every attempt must be denied and logged appropriately.
11. Apply migrations `019–025` to the previous release database and to a clean database; compare schema, membership and account data afterward.
12. Build and start the complete Docker Compose stack from a clean machine; verify health checks, restart behavior and persistent data.

## 8. Release gates

### Mandatory before internal QA/demo

- Use synthetic or explicitly approved non-client test data only.
- Start MariaDB and the API, then obtain a clean automated-suite result.
- Apply migrations `019–025` to the isolated QA database.
- Verify at least one complete browser workflow from sign-in through report output.

### Mandatory before pilot or production

- All automated unit, API, integration and browser E2E tests pass in CI.
- Independent authorization and tenant-isolation review passes.
- Production Firebase, SMTP and secret management are verified.
- Private document storage, malware scanning, encryption, retention and deletion are implemented and tested.
- Backup restoration and recovery objectives are demonstrated.
- Official/approved spatial data provenance and legal-use terms are documented.
- OCR acceptance accuracy is measured against an approved representative corpus.
- Load, accessibility, browser-compatibility and vulnerability testing pass agreed thresholds.
- Product, Engineering, QA, Security and Legal/Data Steward owners sign the release record.
