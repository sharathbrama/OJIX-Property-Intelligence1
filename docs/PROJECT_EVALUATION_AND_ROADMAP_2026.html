IMPORTANT OPERATING PRINCIPLE The platform is an evidence and workflow system. It must not represent AI output as a legal opinion, ownership determination, or government certification. High-impact conclusions remain strictly reviewable and signable by a qualified professional.

1. The Core Need: Why Was This Project Built?

Property due diligence in Karnataka—particularly around Bengaluru—suffers from chronic fragmentation, legal risks, and high-stakes disputes. Due diligence teams previously had to manually cross-examine documents across unconnected departments.

  • Severe Spatial Hazards: Unmapped storm-water drains (Rajakaluve) and mandatory National Green Tribunal (NGT) lake buffer zones (30m, 50m, 75m) frequently intersect properties, triggering government demolitions or registration bans.
  • Fragmented Records: Critical records are siloed across Bhoomi (RTC/Pahani, Mutation extracts), Kaveri 2.0 (Registered Deeds, Encumbrance Certificates), BBMP e-Aasthi (Khata, property tax), and BDA (Layout approvals, Master Plans).
  • Multilingual Discrepancies: Documents mix archaic Kannada terminology with modern English. Area measurements differ between traditional units (Acres, Guntas, Cents) and standard square feet, causing undetected over-conveyance.
  • The AI Hype Trap: A generic AI chatbot cannot be trusted with legal titles. Legal professionals require an unbroken chain of provenance with exact page anchors, bounding boxes, and cryptographic checksums.

4. Defects, Mistakes & Architectural Divergences in Current Code

4.1 Major Architectural Divergence: Database & Framework

FRD Requirement: Google Cloud SQL PostgreSQL with PostGIS and pgvector + NestJS.
Actual Codebase: MariaDB 10.11 + Express.js.
Consequence: MariaDB lacks native vector embeddings (pgvector) for legal research. In addition, using Express led to a monolithic 3,685-line file (apps/api/src/server.ts) that is difficult to maintain compared to modular NestJS controllers and services.

4.2 The "Fake Fallback" Trap (Previously Present, Now Safeguarded)

In earlier iterations, whenever a service failed or had no data, the code fabricated believable demo results:

  • Generating 3 synthetic historical deeds when a title chain was empty.
  • Assuming default central Bengaluru coordinates and a hard-coded 18m buffer distance when spatial queries failed.
  • Serving mock PDF bytes and presenting the output as a "Signed PDF".

Status: These misleading fallbacks were removed and replaced with defensive 501 / unknown responses (see P0-GAP-REGISTER.md). However, the real external service integrations (Playwright PDF renderer, real GIS layers) have not yet been wired up in their place.

4.3 Frontend Bundle Size Bloat

The Vite production build produces a single unchunked JavaScript bundle of ~1.68 MB. All components (MapLibre, Report Viewer, Admin Console) are loaded simultaneously without route-based code-splitting (React.lazy()).

4.4 Test Suite Environment Dependency

Running npm test fails with ECONNREFUSED unless MariaDB is actively running on port 3306. The test suite lacks mocked in-memory database adapters for isolated testing in standard CI/CD environments.

5. Actionable Roadmap & Release Steps

  1. Step 1 — Wire Headless PDF Renderer: Replace the 501 stub in report-generator.ts with Playwright/Puppeteer to produce verified PDF reports.
  2. Step 2 — Ingest Official GIS Layers: Replace the synthetic demo row with genuine BBMP Rajakaluve shapefiles and official Karnataka lake boundaries.
  3. Step 3 — Implement Cloud Object Storage: Migrate file uploads from local disk to a cloud bucket (Google Cloud Storage / S3) with short-lived signed URLs.
  4. Step 4 — Add Async Job Queues: Offload OCR and PDF generation to background workers to prevent HTTP request timeouts.
  5. Step 5 — Frontend Optimization: Split the 1.68 MB bundle into lazy-loaded routes to ensure responsive performance on mobile devices.
